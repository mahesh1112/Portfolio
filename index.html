Multi-Agent Bug-Fixing System

From frontend symptom to the right microservice, validated fix, and developer-reviewed PR.

An orchestrator coordinates 13 agent roles to resolve Jira bugs across 22+ repositories. Frontend reproduction and a microservice/API knowledge base identify the affected service, followed by targeted investigation, gated fixes, validation, and developer review.

⚡ 84% success across 42 defects · 207+ hours saved
Engineering case study+

The problem

Resolve frontend-reported bugs across a microservice architecture spanning more than 22 repositories. More than 90% of issues arrive through the frontend, even when the underlying fault belongs to a backend service.

Contribution & scope

Implemented an orchestrated bug-resolution workflow with Jira analysis, KB-assisted repo detection, bug categorization, frontend and backend investigation, fix proposals, PR-impact analysis, implementation, validation, and developer-driven reiteration.

Design rationale

Reproduce the frontend symptom before choosing a repository. Use exact microservice-to-API mappings from the KB to find the responsible service. Categorize the fault as frontend-only, backend-only, or both, and invoke the applicable agents. Generate a proposal first, check open PRs for impact, and implement only after the green signal.

Results & evidence

Reported evaluation: 84% success across 42 defects and 207+ engineering hours saved.

Evaluation context

The agent validates changes and raises a PR; the developer pulls the bug branch, verifies the fix, and controls merge. Unresolved issues return with developer feedback. After reiteration, the retrospective logs first-iteration mistakes to guide improvement. The frontend quickfix invocation trigger and blocked PR-impact handling are not yet specified.

APPLIED LLM RESEARCH · RAG

HireFlow

Resume ingestion, dual-vector retrieval, deterministic rules, and explainable candidate ranking.

A Next.js and FastAPI screening application that parses resumes and job descriptions with Gemini, indexes three 384-dimensional resume vectors in Pinecone, and combines semantic retrieval with six knockout rules and weighted candidate scoring. PostgreSQL stores profiles, jobs, progress, and results.

3 resume vectors / 6 knockout rules / 4 scoring dimensions
Engineering case study+

The problem

Screen a pool of resumes against a structured job description while combining semantic relevance, explicit eligibility rules, and contextual scoring with recruiter-readable explanations.

Contribution & scope

Project scope covers a JWT-protected Next.js/FastAPI application, asynchronous PDF/DOCX ingestion, Gemini-based resume and JD parsing, local multi-view embeddings, Pinecone retrieval, deterministic knockout rules, scoring fallbacks, and persisted recruiter results.

Design rationale

Separate resume ingestion from screening. Index three semantic views per resume, generate JD query vectors on demand, blend two semantic searches equally, and hydrate profiles from PostgreSQL. Apply hard eligibility rules before the more expensive Gemini scoring stage, then rank passed candidates by weighted fit score.

Results & evidence

The supplied Technical Architecture & Flow Documentation (version 1.0, February 2026) describes the components, processing sequence, formulas, fallback behavior, async concurrency, progress polling, and CSV export. No measured ranking-accuracy or production-scale benchmark is provided.

Evaluation context

The document identifies shared Pinecone namespaces, post-retrieval filtering, ephemeral /tmp file storage, absent skill normalization/ontology and keyword-vector retrieval, and no recruiter-feedback learning loop. Redis is provisioned but not integrated. Tagging, namespace isolation, persistent object storage, and caching are proposed improvements, not completed capabilities.

Next validation step

Evaluate retrieval and ranking against a labeled candidate set, test each knockout and unavailable-service branch, and address durable file storage and tenant isolation before presenting the design as production-ready.

Two different weight systems

Retrieval blends full-profile and skills cosine scores 50%/50% to select a capped candidate pool. Final fit scoring is a separate calculation: skills 40%, experience 25%, career progression 20%, achievements 15%.

Six eligibility rules

The documented rules check experience below 60% of the requirement; missing top-three mandatory recent skills; recent-skill overlap below 20%; an employment gap over 12 months; location mismatch without accepted relocation; and unmatched education-level keywords. These are implemented heuristics described by the document, not evidence of their effectiveness.

Architecture source

Based on the supplied HireFlow Technical Architecture & Flow Documentation, version 1.0, February 2026, especially sections 3-6 and 8-11. Recommendations in sections 12 and 14 are kept separate from current behavior.

COMPUTER VISION · FACE ENCODINGS

Face Recognition Attendance

Face encodings, distance-based matching, and per-subject attendance in a PyQt5 desktop app.

A PyQt5 desktop app that registers students from a webcam photo and marks attendance by face. Each face becomes a 128-dimensional dlib encoding, and a live face matches when its Euclidean distance to the stored encoding is 0.6 or less. MySQL keeps students and one attendance table per subject and day; a multi-face mode identifies everyone in view against all enrolled encodings.

⚡ 92% live recognition accuracy
Engineering case study+

The problem

Take class attendance from a webcam instead of a manual roll call, confirm that the person present is the registered student, and count each student once per subject per day.

Contribution & scope

Project scope covers webcam registration, face encoding and distance-based matching with the face_recognition library, per-subject daily attendance in MySQL with a duplicate check, a PyQt5 interface for registering, marking, and viewing attendance, and a multi-face mode that identifies everyone in view.

Design rationale

Matching works on face encodings rather than raw pixels: each face is reduced to 128 numbers that stay similar for the same person across photos, so a comparison is a single distance calculation. The main app verifies the face against the student who entered the roll number (1:1), which needs one comparison and cannot confuse two enrolled students. The multi-face mode searches all enrolled encodings (1:N) to identify everyone in view without typed input.

Results & evidence

The public source code shows the full registration, matching, and attendance flow. Reported result: 92% live recognition accuracy; the test conditions behind that figure are not yet documented.

Evaluation context

Each student is matched against a single reference photo, and the library's default 0.6 tolerance is used without tuning. Lighting, camera angle, and the number of enrolled students behind the 92% figure are not recorded, and false matches and missed matches are not reported separately.

Next validation step

Measure false-match and missed-match rates across lighting and camera angles, tune the tolerance from those results, enroll several photos per student, add a liveness check, and in multi-face mode select the closest match rather than the first within tolerance.

How two faces are compared

Detect the face with HOG, align it using facial landmarks, encode it with dlib's ResNet into 128 numbers, then measure the Euclidean distance to the reference encoding. A distance of 0.6 or less counts as the same person. The network was trained so that photos of one person land close together, which lets a single threshold separate "same" from "different".

1:1 verification vs 1:N identification

Verification answers "is this the student who entered this roll number?" with one comparison. Identification answers "who is this?" by comparing against every enrolled face, so its work and its chance of a false match grow with class size.

Model benchmark vs this system

The face_recognition library reports 99.38% accuracy for its dlib model on the Labeled Faces in the Wild benchmark. That describes the model on curated photos; the 92% figure is this project's live webcam result.

Architecture source

Based on the public repository mahesh1112/face_recognition, Attendance System folder: test.py (PyQt5 app), dataset.py (registration), test2.py (1:1 attendance marking), and embeddings.py with main.py (multi-face mode).
